# V2.8 滚动预翻译

## 问题

此前只在正文进入可见区域后才发起翻译。首屏可以较快显示，但连续阅读时，每次滚动都会重新承担网络首 token 等待，真实体验取决于 API 延迟。

## 实现

- 首屏仍优先翻译；首屏完成后，默认批量准备下方约 2 屏内容。
- 预取范围可设为关闭、1 屏、2 屏或 3 屏，单次滚动周期另有字符预算，避免长页面持续后台翻译。
- 预取结果只保存在内存中。目标段落进入屏幕后才原位替换，因此不会提前改变页面高度和滚动位置。
- 当前屏幕出现缺失译文时，API 模式取消无关预取并提升可见内容优先级。队列已满时，可见任务可以淘汰尚未开始的预取任务。
- 页面隐藏、用户关闭预取、预取失败或节点变成代码、隐藏、敏感内容时，取消或丢弃对应结果。失败的预取不会立即后台重试，避免重复费用。
- 相同片段继续使用已有去重和缓存，预取与当前屏幕共用同一缓存。

Read Frog 的官方高级翻译说明把“小段落合并”和预翻译距离作为降低等待感的手段，同时指出更大的预翻译范围会处理用户未必阅读的内容。本版采用相同的体验原则，并将范围、字符预算、可见内容抢占和离屏不绘制结合起来：[Read Frog Advanced Translation](https://www.readfrog.app/en/docs/advanced-translation#small-paragraphs-and-pre-translation)。

## 验收

- `npm test`：72 项通过。
- `npm run check`：通过。
- 本地 Chromium 模拟页：首屏请求完成后，第二、第三屏 4 段合成 1 个预取请求；预取完成后离屏 DOM 未改变。滚动到第二屏时 82 ms 显示缓存译文，请求数没有增加，未出现错误覆盖层。

模拟页使用本地可控回复，82 ms 只衡量已有译文从内存写入页面的调度时间。它不包含 DeepSeek 网络延迟，也不等同于竞品或生产页面的端到端速度。
